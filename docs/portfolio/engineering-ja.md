## 課題から設計へ

日本の大学院入試では、研究科共通の要項、専攻別案内、追加提出物一覧に情報が分かれています。単に関連する文章を見つけても、その条項が対象年度・選抜ルート・申請者に適用されるとは限りません。

このプロジェクトでは、教務担当者が繰り返す「探す → 条件を確認する → 原文に戻る → 説明をまとめる」という作業を支援します。本リポジトリでは、塾内の教務支援を目的としたシステムの代表機能を公開デモとして紹介しています。現在は日本のAI職への応募用ポートフォリオとして、実装・検証・設計判断を紹介しています。新しい開発範囲は未定です。

## 実装上の判断

| 課題 | 採用した設計 | 引き受けているコスト |
| --- | --- | --- |
| 検索順位だけでは条件の適用を決められない | 検索とレビュー済みルールを分離。未入力をfalseと同一視しない | 条件と例外を明示的に整理する必要がある |
| 似た学校名・年度・材料名の混同 | 文書・対象の完全な識別、版とハッシュの検証 | レビュー入力から表示・ルール設定を生成し、重複転記を減らす |
| 複数資料を使う説明が不安定になる | 根拠と補足を区別し、レビュー済み文書間関係を保持 | 未整理の関係を自由に推論する機能ではない |
| 毎回の索引生成は時間と資産を浪費する | 通常起動は再利用のみ。構築と有効化を明示的に分ける | PDF・KB・モデル版の不一致では起動を止める |
| 生成文章を正式な判定と誤認しやすい | LLMは参考回答。公式の要求と個人の準備状況を別に扱う | 対応外・未確認を画面でも分かるようにする必要がある |

### 検索の実装

- BGE-M3をSentence Transformersアダプター経由で利用。モデルrevisionと1,024次元を固定。
- 意味検索とBM25を、順位ベースのRRFで統合。
- `CorpusSearchContext`は選択済み文書を監査してから検索する。文書内の同じFact IDが衝突しないよう文書IDと組み合わせる。
- ベクトル索引は `manifest.json`・`payloads.jsonl`・`embeddings.npy`。外部ベクトルDBを必須にせず、ローカル成果物として検証・再利用する。
- 処理基盤としての複数文書検索と、実際のUIで提供する資料範囲は別。東京大学の現行5テーマはレビュー済み設定経由で提供し、自由な東大横断RAG検索を有効化していない。

参照：[検索契約](../corpus-retrieval-v1.md)、[RRF](../evaluation/hybrid-retrieval.md)、[索引契約のADR](../decisions/0001-derived-vector-index-contract.md)。

### 一例：志望調査票を追加する

1. 既存の追加提出物一覧と専攻案内から、対象範囲・提出方法・作成手順を確認する。
2. 原文とページ、条項間の関係、中文の説明、明示的な条件を一つのレビュー入力に整理する。
3. 外部の承認ファイルで、その入力と基底設定の正確なハッシュを固定する。
4. 生成器が既存mapperを使用して、導入設定・policy・plan・出典の対応・表示を機械生成する。
5. 既存のloaderで資料と参照の整合性を検証し、実際の画面・報告と旧設定の互換性を確認する。

新規のルールエンジンや自然言語ルールDSLは作らず、既存の実行系を再利用しました。この材料追加の新候補は約122 KiB、生成設定は約161 KiB。PDF・モデル・ベクトル索引を複製して増やす方式ではありません。ただし、年度更新で内容が変われば再レビューが必要です。

参照：[設定生成の設計判断](../decisions/0017-reviewed-authoring-config-generation.md)、[生成器](../../scripts/m19_configs.py)、[フィールドの出典対応](../onboarding/m19-generated/sources.json)。

## 検証をどう読むか

**評価集合を固定した検索品質**と、**アプリケーションの正しい動作**を別々に確認します。

- 検索：**固定42問・391件のKB、2026-09-24保存レポート**で、ハイブリッド検索のRecall@10は**0.8852**、MRRは**0.8323**。[原レポート](../../tests/fixtures/grounded_rag_retrieval_report_v1.json)の集計値を表示桁で丸めた値であり、全校や任意質問への一般化を示さない。
- 回帰：保存された基準、閾値、対象実装の整合性をCIで検証。CIが毎回モデルを動かして測り直しているわけではない。
- ルール：誤った学校・版・段階、欠けた根拠、未知の入力に対し、肯定的な結論を出さないことを確認。
- UI：デスクトップ／スマートフォン、状態の変更、原文ウィンドウの往復、レポートのコピーを確認。
- 証拠の種類：実HTTP、実資料からの直接投影、保存レスポンスの再生、合成データを区別して記録。

同じ42問でのBM25単独・ベクトル単独の保存結果は未測です。[以前のBM25記録](../evaluation/lexical-retrieval.md)の34問・298件でのヒット件数をRecallやMRRに読み替えていません。方式間の優劣は、現状の記録だけでは結論づけられません。[比較表](../../README.md#評価結果とその読み方)

**Release-subset MRR 0.2455**は、サービス経由の11ケース（中国語の難問や回答拒否ケースを含む）の実際の検索順位で算出した部分集合の値です。**中国語→日本語 hit@10 0.50**は、リリース評価内の対象となる中国語質問で日本語の正解根拠が上位10件に一つ以上入った割合です。両者は42問全体の集計とは区別します。[評価定義](../evaluation/grounded-rag-release-v1.md) / [保存結果](../../tests/fixtures/grounded_rag_evaluation_report_v1.json)

資料追加時は、保存されたHTTP応答を原資料からの独立した投影と照合し、生成設定の再現性と旧設定との互換性を確認しました。ブラウザ検証の範囲と制約は[検証記録](../onboarding/m19-design-acceptance.md)を参照してください。

## 試行から学んだこと

**UIの再利用。** 新機能のために別の画面を増やすより、既存の四段階の流れに統合する方が利用者に伝わりやすいと分かりました。材料の説明、個人状態、参考情報の優先順位を整理し、詳細は必要なときに開く形へ改善しています。

**新しいパーサーを入れる前の比較。** MinerUの限定試行は採用に至りませんでした。実行予算超過や監視処理の問題を含むため、結果を単純なモデル性能比較として扱っていません。公開デモのPDF処理はPyMuPDF/pdfplumberを維持しています。[試行記録](../onboarding/mineru-4.0.7-pilot-report.md)

**自動化する範囲。** 表示データから始め、導入・ルール・報告設定へと機械生成を広げて重複を減らしました。機械的な転記と、資料の意味を承認する作業を分けることで、既存機能を維持しながら資料の追加方法を改善しています。

## AI支援開発と役割分担

生成AIのコーディング支援を活用しています。課題設定・仕様と範囲の判断を人が担い、資料の整理、実装、テスト作成にAgentを利用します。開発用と設計・受入用のAgentを分け、原資料や再現可能な結果に照らして検証し、Issue・PR・ADRに判断と証拠を残しています。

公開リポジトリで示すのは、この設計と検証の過程、および代表機能です。塾内の個別データや後続の非公開業務開発は対象に含めません。

## 今後の検証課題

- 新しい資料を追加するときの、人手による整理・レビュー時間の計測。
- 資料の年度更新で、再利用できる設定と再確認が必要な条項を明確にする。
- 教務担当者による継続試用で、操作性と実際の確認時間を評価する。
- 学生向けの情報量調整、公開運用に必要な認証・運用設計。

これらは計画上の課題であり、今回のREADME更新で開発や公開を開始したものではありません。
